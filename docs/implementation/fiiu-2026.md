# FIIU Fest in NODAL

## Brief and sources

Implement the September 28 request and Flavia's FIIU x NODAL board within the existing plain HTML/CSS/JavaScript and Node architecture. Source form: https://docs.google.com/forms/d/1zvj20L8MqH84WHh0XxsgGfEE1qhEF-X4RgO3QrPP8fk/edit. Event: https://fiiu.sistemaurbano.org/. Board: https://app.clickup.com/4209584/whiteboards/40exg-29877.

The public landing page is linkable before login. Registration uses the existing NODAL account and returns to the festival after authentication. One editable registration per account records five general conference blocks (October 21 morning/evening, October 22 morning/evening, October 23 morning). October 20 is an optional reviewed laboratory application for public officials, never automatic admission. Nine workshops and five routes have individual dates and Google Forms links; NODAL records interest separately from conference registration. Completing the facilitator's Google Form remains necessary, and neither interest nor a link click proves external registration or attendance. A person can register interest without selecting a conference. The closing party remains separately registered. Dates are local to Lima. Programme content may change; display the official programme link.

## Architecture and decisions

Dedicated festival domain, repository and API modules support both SQLite and Supabase. New tables hold private registrations, administrator-confirmed attendance, configurable links/open status, and published news/material links. New Supabase tables have RLS and server-only grants; ownership, administrator permission, same-origin protection, limits and optimistic versions are enforced at the application boundary. Account export and deletion include festival records. Registrations cannot grant roles, laboratory acceptance or badges. CSV exports neutralize spreadsheet formulas.

The form is inspiration: correct its outdated Cusco motivation option to a location-neutral choice. Account email is authoritative. Per the September 29 feedback, identity, age, gender, accessibility, motivation and previous-attendance answers are required. An explicit no-support answer and prefer-not-to-say gender remain valid; Other text is required only when Other is selected. These answers stay private, are never added to public profiles, and are not saved in browser storage. Registration remains subject to venue capacity. Historical incomplete records stay readable, exportable and cancellable; the attendee must complete missing fields on their next save.

The navigation reflects Programa / Comunidad / Recursos / Conocimiento / Mi panel. Existing community and catalog capabilities remain available. A community hub highlights FIIU, urban meetups and events; knowledge connects to existing courses and resources. Published festival news appear on the dashboard, along with the member's registration and earned badges. Only administrator-confirmed attendance earns a badge. News/resources use real published content and honest empty states.

Design follows NODAL's Montserrat typography and green identity: forest #3d5c38, leaf #59bc53, pale green #dcebd6, white #ffffff, ink #20291e. A broad festival title and compact date/venue panel lead into a readable day-by-day programme. Registration uses grouped fieldsets with a visible saved state; the public-official branch stays next to the programme choices. All controls work on mobile, with keyboard focus and English/Spanish/Portuguese interface text.

## October 2: registration summary email

The organisers asked for an automatic confirmation after someone registers. The email must summarise the activities, remind people that workshops and routes still need their Google Form, and link the shared festival Google Calendar.

- **What is sent.** After the **first** registration only (the insert in `PUT /api/fiiu/registration`), `server/fiiu-email.js` builds one email in EN, ES or PT. It uses the page's language, then the `nodal.lang` cookie, then Spanish. The email has a greeting with the first name and the person's choices day by day in programme order: conference blocks with Lima date, time, Spanish title and venue ("Venue to be confirmed" when unknown); the laboratory application and its status; each workshop or route interest with its venue or starting point and its own Google Form link. A reminder that only the Google Form confirms a workshop or route place comes first when there is any; without one, a single general line says that workshops and routes are booked through their own Google Form and links the NODAL programme. The inbox preview line mentions Google Forms only when there is one to complete. Then the shared calendar (`FIIU_EVENT.calendarUrl`), a link back to `/fiiu.html#registration`, and a note that the live programme (`config.programUrl`) is the reference. HTML and plain text. No national ID, age, gender, accessibility, motivation, institution or role.
- **Transport.** `server/mailer.js` is a dependency-free SMTP client: implicit TLS with certificate verification, AUTH PLAIN, RFC 2047 subject, multipart/alternative base64 parts, dot-stuffing and one 8-second deadline. It is configured by `EMAIL_SMTP_URL`, `EMAIL_FROM` and `EMAIL_REPLY_TO` (default `fiiu@ocupatucalle.com`) and works with a Google Workspace app password or an SMTP relay such as Resend. Without those variables the feature is off. Only the Supabase backend sends by default; a local SQLite server only sends to a loopback mail catcher, and tests inject an outbox.
- **State.** `fiiu_registrations` gains `confirmation_status` (`none`, `pending`, `sent`, `failed`, `uncertain`, `skipped`), `confirmation_language` and `confirmation_sent_at`. The migration `20261003013301_fiiu_confirmation_email.sql` is additive; SQLite upgrades in place. The row is inserted as `pending`, the send is awaited (Vercel has no `waitUntil` here), and a compare-and-set on the status alone records the outcome without bumping the version. Email never fails the registration. Reserved test and example domains (including `example.com`, `.net` and `.org`) are `skipped`. The sending allowance (3 per account and 60 overall per hour, per server instance) is spent only after the insert succeeds, and a registration over it stays `none` so the backfill can send it later. A malformed or oversized SMTP reply after the whole message was written counts as `uncertain`, not `failed`, so a retry cannot send a second copy.
- **Where it shows.** After the first save the registration panel says "We emailed a summary to <address>", "Your registration is saved. We could not send the summary email." (`failed`), or "Your registration is saved. The summary email may be delayed or may not arrive." (`uncertain`), the last two as amber warnings. The organiser's participant detail has one line, for example "Summary email: sent · Fri 2 Oct 14:32", and the CSV ends with a `confirmationEmail` column.
- **Backfill.** About 16 people registered before this; by 2 October, 46 production registrations were at `none`. `scripts/send-fiiu-confirmations.js` lists them (dry run). With `--send` it emails them with the same compare-and-set, and `--test-to` sends one sample summary. Its arguments are parsed strictly (`--limit 5` and `--limit=5` both work); anything malformed stops it before any email goes out. The owner decides whether to run it (DEPLOYMENT.md, "FIIU registration summary email").
- **Privacy.** The three policies now say that a summary is emailed after the first registration and that emails go through "the email service NODAL uses to send messages". `web/pages/privacy.html` is regenerated, dated 2 October 2026.
- **Release order.** Apply the migration, then merge. Set the email variables in Vercel for **Production only**, then send a test with `--test-to`.

## October 2: sending the summary from the organiser dashboard

The Gmail credentials live only in Vercel, so the owner asked for the backfill as a button in the organiser dashboard instead of a command run from a machine that holds them.

- **Where.** `fiiu-admin.html#settings`, under "Registration and links": a **Summary emails** block with one line ("46 registrations have not received the summary email · 31 sent · 2 failed"), one press-plate button ("Send the summary to 46 people") and, when there are failures, an underlined "Retry failed (2)". The first press asks in the page ("Confirm: send 46 emails" or Cancel; no browser dialog). The run then shows "Sent 12 of 46…" with a Stop text button and ends with a plain summary ("Sent 44 · Failed 2 — you can retry the failed ones"); the counts and the overview are re-read afterwards. Without a sender the block says the email is off and which variables turn it on, with no button. A 401 shows the page's sign-in notice; a 403 locks the page as everywhere else. Wide screens use the settings' two tracks (heading and note beside the counts and the button). EN, ES and PT.
- **API.** `GET /api/admin/fiiu/confirmations` answers `{configured, counts:{none, pending, sent, failed, uncertain, skipped}, dailyCap, sentToday, resetsAt}`. `POST` with `{retryFailed?, after?}` sends **one batch**: at most 4 registrations, after the `after` cursor in id order, emailed concurrently with the mailer's 8-second cap, so a request ends well inside Vercel's function limit; the page keeps posting with the answer's `next` until `remaining` is 0. The cursor also keeps a retry pass from picking a row that just failed again. Administrators only, same-origin, rate limited by the existing FIIU write limiter (30 a minute; the page pauses half a minute on a plain 429). 503 `email_not_configured` without a sender.
- **Once per person.** Each row is claimed with the same compare-and-set as the first-registration send (`none` → `pending`, or `failed` → `pending` on a retry) before its email goes out; a press that loses the claim counts it as `claimedElsewhere`. Two organisers at once, a double click, or the dashboard and the script together never email anyone twice (tested by three presses that all read the same rows). A send that throws is `uncertain`; a row whose outcome cannot be written stays `pending`, the request fails, and nobody resends it.
- **Daily cap.** 150 summary emails per UTC day, counted in the database from `confirmation_sent_at` (sign-up emails included, so every instance agrees and the Gmail account's ~500 a day keep room for sign-ups and password emails). It counts every send that may have reached the provider: `confirmation_sent_at` is stamped when a row turns `pending` (the sign-up insert, or the button's claim), replaced by the acceptance time for `sent`, kept for `uncertain`, and cleared for `failed` and `skipped`; the count is `confirmation_status IN ('sent','uncertain','pending')` since the start of the UTC day. So a mail server that answers too slowly, leaving every send `uncertain`, still stops the button at the cap. At the cap the API answers 429 `daily_cap` and the page says sending can continue after 19:00 Lima time. Two organisers pressing at the very same moment can pass it by at most one batch each, and a registration cancelled the same day takes its email out of the count (its row is deleted). Gmail's quota is a rolling 24 hours; two UTC days back to back can put twice the cap (300) inside 24 hours, still under it. Sign-ups are never held back by it. No migration: the store's `count` gained an id cursor, an "at or after" time filter and a one-of filter (`gt.`/`gte.`/`in.` in PostgREST).
- **Shared code.** `server/fiiu-confirmations.js` holds the claim-send-record step, the counts, the batch and the command-line loop; `scripts/send-fiiu-confirmations.js` keeps its flags, output and tests and now calls it.
- **Tests.** API (`tests/fiiu.test.js`): batches of four, stored language, reserved addresses skipped, uncertain and pending never resent, three concurrent presses, the retry cursor, the daily cap and its reset (uncertain, in-flight and sign-up sends counted, failed ones not, also through a mail server that takes each message and never answers), access, CSRF and validation, a failed outcome write, and an end-to-end run through the real sender and a loopback SMTP server. PostgREST (`tests/fiiu-supabase.test.js`): exact counts, compare-and-set claims, the keyset cursor and the cap. UI (`tests/fiiu-admin-ui.test.js`): every block state, the in-page confirmation, live progress, Stop, Cancel, Retry, the cap, email off, 401, 403, a failed request, the write-budget pause and Stop pressed while a request meets that budget.

## October 3 full review

A full-platform review (auth, sessions, payments, courses, FIIU, email, database, front end, config) on branch `fix/full-review`, fixed by area and then integrated. Regression tests for each finding are in `tests/review-fix-1…5-*.test.js`; fixes from earlier audits were not reopened.

**Fixed**

- **Sessions and sign-in.** The Supabase session gate checks cookies before GoTrue: a missing, expired or non-JWT access token is never sent to `/auth/v1/user`, and rejected refreshes are budgeted per client address (`SESSION_REFRESH_FAILURE_LIMIT`, 30 per 5 min). Routes that never use a session skip it; id-only routes read one profile row instead of three tables. A GoTrue outage serves `/login.html` and the public APIs signed out, and private pages get a small trilingual 503 page. Only wrong passwords count against sign-in (per email and address, plus 50 per email across addresses), so nobody can lock an owner out. Sign-ups stop at 200 an hour per instance, keeping Supabase's 300 emails an hour for recovery and invitations. Recovery is limited per email and requester and answers 429 `recovery_rate` instead of a silent "sent". Sign-up answers the same for new, unconfirmed and confirmed addresses and writes no profile. Logout also revokes through the refresh token; a sign-out keeps its unit of the refresh budget only when Supabase rejects that token, so a class signing out together does not use up the budget its classmates' session refreshes need. Passwords are limited to the provider's 72 UTF-8 bytes on the server and in the sign-up, recovery and invitation forms (EN/ES/PT copy says "8–72 characters"), before any one-time link is spent. Course-invitation completion gets the classroom budget per address and a strict budget per token.
- **Payments.** A second checkout while a subscription is live answers 409 `already_subscribed`; the membership page turns its buttons off for a live status and explains the refusal in EN/ES/PT. Checkout sessions carry an Idempotency-Key per member, cycle and 10-minute window. A completed Checkout Session activates a membership only in subscription mode, with a subscription and with NODAL's `metadata.nodal_user_id` (a Payment Link no longer can). Account deletion waits until the membership is cancelled (409 `subscription_active`, translated in the console). The renewal date is read from the subscription item on Stripe's 2025 API.
- **Courses.** Downloads are cacheable per file (ETag, 304) and limited to 64 MiB per 10 min and 512 MiB a day per member account; staff, who open a whole class's files when reviewing, are not limited. Withdrawn or moderated posts release their files; authors can read and withdraw their own posts after the course closes. Activity events are one per participant, resource and hour; feedback stops at 200 per account (`feedback_limit`, translated). Upload names get their type's extension and lose control and bidi characters, also for files stored earlier. `npm run uploads:reconcile` also finishes interrupted deletions and removes orphaned post uploads.
- **FIIU.** An edited retry of a publication under the same editor id is a 409 conflict, not a silent "saved". The summary email is off on any Vercel deployment that is not Production. Send failures log a safe error code. The backfill applies the daily cap before every email (`--ignore-cap` overrides it on purpose).
- **Data and performance.** Catalog open-state and paging are filtered by PostgREST with a keyset cursor and at most 8 batches per request. Network snapshots are reused while the revision is unchanged. Unlisted members' recommendations are looked up by revision before any graph is read. Failed geocoding is remembered for 10 minutes, and one globe poll waits at most 2 s on the geocoder. Short course pages take one PostgREST request. Profile lists (interests, skills, availability, goals) are capped at 80 characters per item on SQLite and Supabase, on write and on read.
- **Front end.** Safari before 16 (iOS 15) can accept invitations, poll the globe, add course participants and start checkout (no unguarded `AbortSignal.timeout`). With reduced motion the globe draws only when something changes. "Export my data" no longer cancels its own download. `?view=constructor` and similar names no longer break the course tabs. An edited post resend after a conflict gets a fresh id. The SMTP reply reader is bounded.
- **Config and repo.** Boot fails on Vercel Production without `TRUST_PROXY=true` and an explicit https `PUBLIC_BASE_URL`, and on any `TRUST_PROXY` other than `true`/`false`. `NODE_ENV` is no longer suggested as a Vercel variable, and `vercel.json` installs with `npm ci --include=dev`. `.gitignore` keeps AI-tool folders out with a test. DEPLOYMENT.md explains why `supabase db push` must never run against production.
- **Migrations (apply by hand, see DEPLOYMENT.md).** `20261003201144_course_posts_revision_definer.sql` lets Supabase Auth delete an account that has posted in a course (it failed with 42501 before). `20261003201338_close_client_grants_on_server_tables.sql` revokes the browser roles' leftover rights on `organizations`, `organization_memberships`, `stripe_events`, `set_updated_at()` and one sequence. Both are additive or revoke-only, idempotent, and safe with the code that is live now.

**Deliberately not done (needs a decision, the Supabase dashboard or a production migration)**

- **CAPTCHA on sign-up** (auth-1): one address can still use up an instance's 200 sign-ups an hour. Only Turnstile or hCaptcha closes this, and that needs CSP and page changes.
- **Password set at email confirmation** (auth-2) and **token-hash password recovery** (auth-5): both need a custom Supabase email template switched in the same deploy as new pages and routes. Signing up no longer writes a profile or reveals membership, which removes the main harm meanwhile.
- **Durable FIIU send ledger** (fiiu-1): registering and cancelling in a loop can still take sends out of the daily count, because the count reads registration rows. The full design (a `fiiu_email_sends` table, a per-account daily limit) needs a production migration; the server comment that overstated the hourly ceiling is corrected.
- **Stripe events for an older subscription** (catalog-news-payments-1, database part) and **keeping an anonymised billing row after deletion** (database-2): need an `apply_stripe_event` migration and a privacy-policy decision. Latent while `PILOT_MODE` is on; the 409 guards above prevent the double subscription in the first place. Reusing a stored Stripe customer on a new checkout also waits for that change.
- **Profile save writes** (performance-6): skipping no-op writes and the re-read after saving changes the tested city/pin race guard; left for a separate change.
- **Adding a participant who has not signed in yet:** a profile is now written at the first sign-in, not at sign-up, so staff adding by email someone who confirmed their address but never signed in get "not found", and the email invitation then fails because the account exists. It resolves at that person's first sign-in; looking the account up in Supabase Auth by email (or a profile written at confirmation) needs a decision.
- **Unlisted recommendations on a cache miss** (performance-2 remainder) still load the whole graph; **per-thread revision counters** (courses-8) need new columns.
- **Optional items not taken:** a CDN `s-maxage` on the anonymous catalog (Vercel's CDN does not key on cookies, so a member's view could be cached), a separate download count limiter (bytes are already bounded), a shared test bootstrap that clears `NODE_ENV`/email variables, and `ALTER DEFAULT PRIVILEGES` so new tables start closed (a persistent setting for the owner to approve).
